### Target definition (binary direction)

Implemented in `src/data.py`:

- Compute daily log return: \( \log(\text{Close}_t/\text{Close}_{t-1}) \)
- Next-day label uses the next trading day return:
  - `target[t] = 1` iff `log_return[t+1] > 0`
  - last row has no `t+1`, so it is dropped

This is a clean “tomorrow up vs down” classification target.

### Feature leakage rule (what “no lookahead” means here)

- Features are engineered at time \(t\) using only information available at or before \(t\).
- The label uses \(t+1\), so the only lookahead is in the target by definition, not in the features.

If you add any feature that peeks at \(t+1\) (or uses centered windows), it breaks the thesis.

### Validation protocol (purged walk-forward + embargo)

Implemented in `src/validation.py`, parameterized by `config.yaml`.

Fold construction:

- Train window: `train_years = 5` calendar years ending the day before the fold’s first test date.
- Test window: 126 trading rows (≈ 6 months) starting at the first row with date ≥ test start.
- Purge: drop the last `purge_days = 200` trading rows from the raw train window (removes boundary contamination).
- Embargo / advance rule: after each fold, the next fold’s test start cursor is advanced by:
  - `test_months = 6` calendar months
  - plus `embargo_days = 10` calendar days

This is implemented with pandas `DateOffset(months=..., days=...)`, so it is calendar time, not trading rows.

This is the core claim of the project. These numbers must be reported consistently in the Report.

### Baselines and models (the comparison set)

Produced in `src/train.py`:

- Baselines:
  - `majority`: majority class from the training window
  - `naive`: “same-day momentum” sign rule (predict using today’s realized return sign)
  - `logistic`: logistic regression with time-series CV inside the fold
- Models:
  - `rf`: `RandomForestClassifier`, randomized search, scoring = ROC AUC
  - `xgb`: XGBoost classifier, randomized search

XGBoost availability rule (important for examiner machines):

If `xgboost` cannot be imported, the pipeline should still be considered a valid submission run as long as:

- baselines (`majority`, `naive`, `logistic`) run, and
- `rf` runs, and
- the artifact contract below is satisfied (even if it lacks any `xgb_*` model pickle).

In other words, XGBoost is a “nice to have” for demonstration depth, not a hard dependency for reproducibility.

### Metrics (what you report)

Written by `src/evaluate.py`:

- Per-fold metrics: accuracy, precision, recall, f1, roc_auc, log_loss
- Aggregates: bootstrap CIs over fold-level metric values
- Significance:
  - paired t-tests on per-fold accuracy (Holm correction)
  - Diebold-Mariano test on Brier scores (pooled), `max_lag=5`

### Reproducibility knobs

From `config.yaml`:

- Seed: 42 (used for NumPy and sklearn, via `src/seed.py`)

Quick determinism note:

- Bootstrap CIs are seeded via NumPy RNG with `config.seed`.
- Any run-to-run drift should be treated as a bug unless the environment materially changed (e.g., different dataset file).
